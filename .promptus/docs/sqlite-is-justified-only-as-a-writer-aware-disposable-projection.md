# SQLite is justified only as a writer-aware disposable projection

The measured threshold for developing a disposable SQLite projection has been crossed, but only under a writer-aware contract. On the frozen MoT snapshot, a clean SQLite build preserved the canonical unit digest and the current lexical result keys and floating-point scores across rebuilds, filtered and phrase queries, one write, and ten writes. Known governed mutations were cheap because the transaction updated exactly the affected units: one new ledger head also invalidates the former final entry whose text slice used to extend to the append sentinel. A blind file watcher cannot infer this dependency and replacing the whole 2,979-entry ledger was no faster than a full index. SQLite is therefore an implementation vehicle for dependency-aware incremental projection, not a substitute for dependency design.\n\nThe trust boundary remains unchanged. Markdown is authoritative. A clean database is built at a temporary path, integrity-checked, and atomically installed; an incremental transaction is serialized with the governed source mutation. The cache stores a source manifest and generation, but the generation is only a fast governed-write receipt. It cannot certify against freehand or external edits. Session doctor and the authoritative full gate must continue exact content verification, reject an ambiguous generation, and delete or rebuild any mismatched database. Network-filesystem portability must not depend on WAL. The exact existing status-aware lexical postings and ranking remain the behavior; FTS ranking is not an implicit replacement.\n\nThe benefit is narrow and useful. SQLite reduced fresh one-query startup sevenfold and writer-aware derived refresh roughly fortyfold, while structured lifecycle, relation, and artifact counts became sub-millisecond joins. It did not improve a persistent in-memory query suite, clean build, blind changed-file refresh, or storage: the clean build was 1.57x slower and the database 3.01x larger than current index files. Consequently there is no case for a daemon, a source-of-truth migration, DuckDB in the write path, or unconditional database use in small stores.\n\nThe engineering sequence is: first land the already-measured work-conservation changes that need no database, define a mutation receipt under the existing store lock including relation and ledger-boundary dependants, add batch writes, then run SQLite in shadow mode beside current derived files. Promote it only after fault-injection, concurrent-reader/writer, relation-lifecycle, external-edit, database-deletion, and cross-filesystem tests all converge to current outputs. A full Markdown rebuild must always remain the recovery path.
